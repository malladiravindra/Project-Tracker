1. PROJECT OVERVIEW AND TECHNOLOGY STACK
--------------------------------------------------------------------------------
Project Tracker is an executive dashboard for projects, tasks, deadlines and team workload.
Tabs: Overview, Tasks & Deadlines, Projects, Team. Extras: Weekly Brief, Global Search, Decision History,
Daily Work Updates, Activity feed, light/dark theme.

Frontend : Next.js 16.4.0 (Turbopack, Cache Components), React 19.3.0, TypeScript, Tailwind CSS 4, ESLint 9.
           Tests: Node built-in test runner (frontend/tests/*.test.mjs).
Backend  : Python 3.14.4 (as run here), Django 5.2.x (requirements: >=5.2,<5.3), Django REST Framework >=3.16,
           django-cors-headers >=4.7. APIView + explicit path() routing only. SQLite (backend/db.sqlite3, git-ignored).
           Optional PostgreSQL settings exist (PostgreSQL-only concurrency tests are skipped on SQLite).
Repository : https://github.com/guravaiahnaidu/Project_Tracker.git
Working branch : backend-integration (tracks origin/backend-integration)
Other branches : main (local fdfec08; origin/main ce57afa), backup/backend-integration-pre-guru-sync (7bf5ccf, local only)
Time zone : server decides "today" (DJANGO_TIME_ZONE, default Asia/Kolkata); the frontend follows the server clock.

8. KNOWN BUGS, SECURITY CONCERNS, TECHNICAL DEBT, PENDING WORK
--------------------------------------------------------------------------------
Bugs / risks found 15 Oct (reported, NOT fixed):
 B1. PATCH /api/members/<id>/ with a membership item lacking project_id returns HTTP 500 (KeyError 'project' at
     backend/members/serializers.py validate_memberships, line ~117). UI always sends project_id so it is not
     reachable from the browser. Fix: use item.get("project") and raise a validation error.
 B2. New Project form defaults status to "Planning" and always sends phase (ProjectsView.tsx ~330, ~452), bypassing the
     server's derivation from the start date.
 B3. A task with a past work date and no due date is grouped as "overdue" ("Work date N days ago"); confirm intent.
 B4. TaskEditor preview uses a stale workOffset until saved (display only).
 B5. Behaviour change: a manual daily-update share for a person/project/day that already has an auto-created update
     returns 409 "already exists".
Security:
 S1. NO AUTHENTICATION OR AUTHORISATION: DRF default permission AllowAny; every endpoint including delete is open
     (documented in README and empty.txt). Do not expose publicly. Production start-up requires
     DJANGO_ACKNOWLEDGE_NO_AUTH=true.
 S2. Manager identity is a fixed server label ("Manager"); no real user model.
 S3. /admin/ is enabled (admin classes were customised in 7bf5ccf); empty.txt recommended removing it if unused.
 S4. Python dependencies are not pinned (ranges only); npm audit findings not reviewed.
Technical debt:
 T1. README.md still says the API is under /api/v1/ (lines 11 and 46) - routes are now /api/. frontend/.env.local.example
     is already /api. empty.txt earlier sections also still mention /api/v1.
 T2. README does not document Guru's work-date / optional-field features or the 6 new migrations.
 T3. Migration 0004 and updates 0003 were generated with Django 5.2.18, 0005-0007 with 5.1.6 (installed: 5.2.17).
 T4. Large frontend components (ProjectsView 1,353 lines, TasksView 1,180, Views 1,097) mix form logic and display.
 T5. Reads are hand-written dict builders, not DRF output serializers.
 T6. Frontend has only 24 unit tests (clock, blocked note, activity merge); no component or end-to-end tests; no CI.
 T7. Deleting tasks/projects purges activity history by design; no soft delete or undo.
Pending (from empty.txt and this review): authentication/roles decision; UI for employees to submit daily updates;
 UI for deleting objectives; concurrency behaviour only provable on PostgreSQL (SQLite serialises writes).
