Application architecture
- Single-page dashboard. ONE Next.js route `/` renders `<Dashboard/>` (app/page.tsx:1-5). Navigation between "pages" is client-side tab state, not URL routing (components/Dashboard.tsx:13, Header.tsx:5). Consequence: no deep links; refresh always returns to the Overview tab.
- Modals/popups: TaskEditor (task popup), WeeklyBrief (popup), generic `Modal` (new project, new task, add employee, activity history).
- The viewer is implicitly a single executive ("You updated...", "Waiting on your decision"). There is no concept of a signed-in user anywhere in the code.
- Dates are stored as integer DAY OFFSETS FROM TODAY (`startOffset`, `endOffset`, `dueOffset`), and event times as `minutesAgo` (lib/data.ts:1-2, 22-23, 36). These must become absolute DATE / TIMESTAMP values in a real backend (see 6.x, 9).

Limitations of this audit
- node_modules is not installed in this checkout, so the bundled Next.js docs referenced by AGENTS.md (node_modules/next/dist/docs/) could not be read. Not needed for this frontend-only audit, but MUST be read before writing integration code because Next 16.4 with `cacheComponents`/`partialPrefetching` may change how data fetching/caching works (see section 16).
- app/globals.css (170 lines) was only sampled (design tokens/theme variables, grep for colors); it contains no data logic. Print styles (`brief-print-root`, WeeklyBrief.tsx:258) were not reviewed in detail.
- public/ contains only default create-next-app SVGs (file/globe/next/vercel/window.svg), unused by the app logic.
- No browser run/screenshots; findings come from reading source only.

### 2.3 Cross-tab navigation rules (Dashboard.tsx:24-49)
- Opening a project (from any list) -> closes task/brief popups, sets Projects tab with that project pre-selected, scrolls to top.
- Opening a task -> opens TaskEditor popup (no tab change).

- Changing tab resets Tasks focus, Team "show" filter and Projects focus.

### M8. Decisions (a project field + workflow)
`Project.decision?: string` = what leadership must decide. Set by editing the "Needs your decision" input in Project detail (ProjectsView.tsx:450-458); listed in Overview DecisionsCard and Weekly Brief; "Mark as decided" clears the field and logs (Overview.tsx:279-288); Undo restores it in-session only (290-301). No decision history table exists in the frontend; the decision text is overwritten/cleared.

## 6. USER WORKFLOWS AND STATUS TRANSITIONS
------------------------------------------------------------------------------
### 6.1 Task status (TaskState)
States: not-started, in-progress, blocked, done. Frontend permits ANY transition (a select; no restrictions, including done -> any, "Mark as done" button hidden when already done, TaskEditor.tsx:317). Constraints: entering `blocked` via the editor requires a non-empty note (89-96). Via the inline row select there is NO note requirement (mismatch, A10). New tasks always start not-started. Deleting a task is a hard delete in the UI.
Task urgency groups (derived) are not statuses and must not be stored.

### 6.2 Project phase (ProjectPhase) - set manually by the lead
Not Started, In Progress, At Risk, On Hold, Completed. Free transitions via select. Default on create: Not Started if start date in the future else In Progress. `phase` only affects: timeLeft ("Completed"), healthPoints bullets for At Risk / On Hold. It does NOT change derived health (`projectStatus`) and does not force `done`=100.

### 6.3 Project health (derived, never set)
off-track / watch / on-track / not-started per 4.11. Health drives: ordering, KPI counts, attention feed, brief sections, Timeline colour.

### 6.4 Decision workflow
(Lead/anyone) enters decision text on project -> appears in Overview "Waiting on your decision" + brief -> executive clicks "Mark as decided" -> decision text cleared, log entry added -> optional Undo (session only). A project holds at most ONE decision string at a time.

### 6.5 Project lead change
Select new lead -> previous lead's role becomes "Team Member" (kept on team), new lead moved to "Project Lead" row, history logged.

### 6.6 Employee onboarding
Add employee -> optional project memberships with roles -> logs -> card highlighted.

### 6.7 Cross-entity effects
- Task owner appears in Team workload; Team "open tasks"/"overdue"/"blocked" counts come from tasks by owner NAME (Views.tsx:45-54).
- Removing a member from a project does NOT reassign or unassign their tasks; deleting tasks has no cascade; there is no project deletion workflow.

B4. DERIVED RULES (single implementation each; all taken from lib/data.ts and TasksView.tsx)
------------------------------------------------------------------------------
- time_used = clamp(round(-start_offset / (end - start) * 100), 0, 100); .5 rounds UP (JS Math.round semantics).
- health: used == 0 and progress == 0 -> not-started; gap = used - progress; gap > 15 off-track; gap > 3 watch; else on-track.
- Task group (done and blocked override dates): overdue (<0 days), today (0), next2 (1-2), week (3-7), later (>7).
- Task bucket: done, blocked, overdue, today, upcoming. Workload kind: overdue, blocked, soon (due <= 7 days), later.
- due_label: "Done", "Blocked", "N day(s) overdue", "Due today", "Due tomorrow", "Due in N days".
- Key dates: project end 0..N days, project start 1..N days, soonest first (Overview N=30, brief N=14).
- Attention feed order: off-track projects, overdue tasks (earliest first), blocked tasks, watch projects, tasks due today.
- Decisions: projects with a non-empty decision, ordered by health rank (off-track, watch, on-track, not-started) then end date.
- Weekly brief "due in 7 days": not done, due 0..7 days.
- Project create: phase = Not Started if start_date > today else In Progress; progress 0; lead added as "Project Lead";
  department blank -> "General".
- Lead change: previous lead's role becomes "Team Member" (stays on the team); new lead is added or promoted to "Project Lead";
  exactly one "Project Lead" row remains. The lead can never be removed from the project (409).

D7. PROPOSED AUTHENTICATION AND ROLE DESIGN (PROPOSAL ONLY - NOT IMPLEMENTED, AWAITING APPROVAL)
------------------------------------------------------------------------------
Why it is only a proposal: adding login changes every API response for anonymous callers (401/403) and the whole frontend flow (login screen,
cookies/CORS, "You" in activity text). Doing it half-way would break the working app, so nothing was enabled. Safe interim measure that WAS implemented:
production mode refuses to start unless DJANGO_ACKNOWLEDGE_NO_AUTH=true, i.e. an operator must consciously state that access is restricted outside the app
(VPN, firewall, authenticating reverse proxy). Development behaviour is unchanged (open API on localhost).

Decisions needed from you before implementation (each changes the design):
 1. Who logs in: only the executive + project leads + administrators, or every team member? One shared executive account or individual accounts? (Q1/Q2)
 2. Can ordinary users see every project/task/member (current UI assumes yes) or only their own projects?
 3. Deployment shape: same registrable domain for frontend and API (enables same-site session cookies) or different domains (needs token-based auth)?
 4. Link between login and Member records: 1:1 (a person logs in as themself) or independent? (Q3)
 5. Should past activity text ("You ...") be rewritten to named actors? (see "Audit actor")

Proposed design (smallest design that meets the requirement):
 Accounts   Django's built-in auth.User (already installed) plus one small model in a new `accounts` app:
            Profile(user OneToOne, member OneToOne NULL -> members.Member, role in {"admin","user"}).  "admin" = project administrator (also the executive
            if you want one seat), "user" = ordinary user. Superuser stays a break-glass Django admin account.
 Auth       Session authentication with HttpOnly cookies + CSRF (SessionAuthentication) when frontend and API are same-site (decision 3a); otherwise short-lived
            access token in an HttpOnly cookie (3b). Endpoints: POST /api/v1/auth/login/, POST /api/v1/auth/logout/, GET /api/v1/auth/me/ -> {id, username,
            display_name, role, member_id}, GET /api/v1/auth/csrf/. Login throttled (DRF throttling) and lockout/backoff on repeated failures.
            Frontend: login page, 401 -> login redirect, fetch with credentials, CORS_ALLOW_CREDENTIALS with the exact https origin (already restricted in production).
 Permissions  (DRF BasePermission classes, one per rule, applied per APIView; no new architecture)
            read (all GET)                         any authenticated user
            tasks: create / update / complete      admin, project lead, project member, or the task owner
            tasks: delete                          admin or project lead
            projects: create, delete, lead change  admin
            projects: phase, dates, progress, objectives, members, decision text   admin or that project's lead
            decision: resolve / undo               admin (the "executive")
            members: create / update / delete      admin
            activity                               read-only for all authenticated users
            Object-level checks live in has_object_permission helpers (IsProjectLeadOrAdmin, IsTaskParticipantOrAdmin) and are enforced in the views that
            already load the object (get_project / get_task / get_member), so a user cannot act on a project they do not belong to by guessing ids.
 Audit actor  ActivityLog gains actor (FK User, NULL, SET_NULL) and actor_name (snapshot, survives user deletion); activity.services.log() takes the request user.
            Stored text keeps its wording; the UI can render "You" when actor == me and the actor's name otherwise. Existing rows keep actor NULL ("System/unknown").
            This is an additive migration (nullable columns), no history is rewritten.
 Rollout in small, reversible steps (flag DJANGO_REQUIRE_AUTH, default false in development, true in production once step 4 ships):
            1 add accounts models/endpoints + tests, no enforcement      2 frontend login/me/logout behind the flag     3 enforce IsAuthenticated + role/object
            permissions with a per-endpoint test matrix (401/403/200 for admin, lead, member, outsider)     4 add actor to the audit log     5 remove the
            DJANGO_ACKNOWLEDGE_NO_AUTH escape hatch.
 Tests planned: permission matrix per endpoint and role, object-level access (other project's task/member), CSRF on unsafe methods, login throttling, actor recorded on
            every mutation, anonymous requests rejected in production mode, development flag still allows the current open workflow.

## AUDIT 2026-10-14 (second pass): confirmed defects, fixes, remaining risks
==============================================================================
CONFIRMED DEFECTS (fixed, with regression tests)
1. [Security, medium] POST /daily-updates/<id>/feedback/ accepted a client-supplied `manager_name`, i.e. a caller could
   impersonate any manager. Fix: field removed; the actor label is server-set ("Manager") until real authentication exists.
   Tests: updates/tests.py::test_feedback_appends_and_sets_status (supplied name ignored).
2. [Reliability] Failed "mark reviewed" was swallowed silently. Fix: lib/dailyUpdates.ts throws; DailyUpdates.tsx shows the
   server message with a Retry button; status stays "New" (it only changes after the server accepts). Verified in browser.
3. [Consistency] resolve/undo of a decision and feedback/PATCH on updates read-then-wrote without a row lock. Fix:
   select_for_update inside the existing transactions (effective on PostgreSQL/MySQL; SQLite serialises writes anyway).
   Tests: repeated resolve -> 400, repeated undo -> 404, undo through another project's URL -> 404, only the latest
   resolution undoable (409).
4. [Scalability] decision-history and daily-updates lists were unbounded. Fix: limit (default 500, max 1000) / offset with
   total `count`; invalid values -> 400. Indexes added (updates 0002, projects 0003).
5. [Earlier, fixed] progress slider lost a second step made during an in-flight save (ProjectsView).

AUTHENTICATION / AUTHORISATION - VERIFIED, NOT IMPLEMENTED (product decision required)
Verified in config/settings.py: DEFAULT_AUTHENTICATION_CLASSES = [], DEFAULT_PERMISSION_CLASSES = AllowAny. Every endpoint
(members, projects, tasks, updates, feedback, decisions incl. resolve/undo, progress) can be read and changed by anyone who
can reach the API. No user/role model exists and the product has no login screen, so adding authentication means choosing
identity provider, roles (manager vs employee), and the manager-to-employee relation; that was NOT invented here.
Consequences until decided: any caller can post a daily update as any employee and can review or give feedback as "the
manager"; tests proving "unauthorised users are refused" cannot exist yet. Production startup already refuses to run
unless DJANGO_ACKNOWLEDGE_NO_AUTH=true (plus secret key, hosts, https CORS). Do NOT expose this API publicly.
Checked and sound: protected fields (employee, project, date) cannot be changed via PATCH; feedback is bound to the URL's
update; undo is bound to the URL's project; CORS limited to configured origins; DEBUG off and a strong secret enforced in production.

DECISION UNDO SEMANTICS: undo deletes the DecisionRecord and the resolve activity entry (established behaviour, covered by
existing tests). A reversal audit trail would be a product change; not made.

NOT DONE: no UI for employees to submit daily updates (API exists). Without authentication such a form would let anyone
submit as anyone, so it is deferred with the authentication decision. No UI for deleting projects/members/objectives.

### H. Security and Validation

### 3. Throttling (COMPLETED, tested with the Django test client; not load-tested)
- config/throttling.py, enabled globally through REST_FRAMEWORK: bucket "write" (POST/PUT/PATCH/DELETE) default 120/min and

- Tests (config/test_reliability.py::ThrottleTests): ten dashboard refreshes plus a write succeed under the defaults;
  the (N+1)th write returns 429 with the JSON envelope (code "throttled") and a Retry-After header and the throttled write

  reset the limit; rejected (400) requests still count.
- LIMITS OF THIS PROTECTION: counters are in Django's default per-process cache, so with several workers each counts on its

Routes (backend/config/urls.py; explicit path()/include(), APIView only, no routers). Every API route ends with "/".
  /admin/                          Django administration
  /api/members/                    members/urls.py:    "", departments/, <id>/
  /api/projects/                   projects/urls.py:   "", <id>/, <id>/history|tasks|members|objectives|decision/, .../members/<member_id>/,
                                                       .../objectives/<objective_id>/, <id>/decision/resolve|undo/
  /api/tasks/                      tasks/urls.py:      "", <id>/, <id>/complete/
  /api/activity/                   activity/urls.py:   ""
  /api/daily-updates/              updates/urls.py:    "", <id>/, <id>/feedback/
  /api/dashboard/                  dashboard/urls.py:  summary/, attention/, key-dates/, team-workload/, decisions/
  /api/decision-history/           single endpoint
  /api/today/                      single endpoint
  /api/weekly-brief/               single endpoint
The old un-prefixed paths (/members/, /tasks/, ...) are NOT kept: no compatibility aliases, no duplicate patterns.

Browser / error behaviour
  /  and any URL outside /admin/ and /api/   -> Django's standard HTML 404 (no homepage, no catch-all). With DEBUG on this is Django's
                                                technical 404 page; with DEBUG off the plain "Not Found" page. No traceback in production.
  /api/<unknown>/                            -> JSON 404 envelope {"error": {"code": "not_found", "message", "fields"}} (catch-all mounted only at api/).
  /api/<known route without trailing slash>  -> 308 redirect to the slashed URL (keeps method and body).
  Outside /api/ a missing slash follows Django's APPEND_SLASH (301) only for URLs that exist, which none do; so they 404.
  Validation/conflict/throttle errors on real endpoints keep the JSON envelope (common/exceptions.py).
  handler500 (common.views.server_error): JSON envelope for /api/ URLs, Django's plain HTML 500 page elsewhere (admin, browser URLs).

Folder layout (backend/)
  config/   __init__.py asgi.py settings.py urls.py wsgi.py          (only these)
  common/   __init__.py apps.py exceptions.py limits.py params.py throttling.py views.py     (shared infrastructure; registered in INSTALLED_APPS)
  tests/    __init__.py support.py (was config/testing.py) audit_support.py test_*.py        (plain package, no models/migrations)
  App-level tests (members/tests.py, projects/tests.py, ...) stay in their apps and import tests.support.
  Run: python manage.py test   (discovers tests/ and the app tests; 190 tests, 5 PostgreSQL-only tests skip on SQLite)

Frontend: lib/api.ts API_BASE_URL defaults to http://127.0.0.1:8000/api; frontend/.env.local.example sets NEXT_PUBLIC_API_BASE_URL=http://127.0.0.1:8000/api.
  A local frontend/.env.local (git-ignored, not edited here) that still says http://127.0.0.1:8000 must be changed to .../api, otherwise every call 404s.
